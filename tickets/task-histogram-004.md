## Observation

Postfix `?` is rejected inside a helper procedure that declares the `error`
effect but returns a plain (non-Result) value such as Int:

    proc parse_uint(s: Str, min: Int) [error] -> Int {
      let t = s.trim()
      ...
      let _ = "".parse_int()?    # check.try-context: `?` requires a Result-returning context
      ...
    }

The checker reports `check.try-context: `?` requires a Result-returning
context` even though the proc declares `[error]`. The same `?` is accepted in
`main` (which returns Unit) and inside stream-stage blocks nested in `main`.
This asymmetry forces the agent to either inline all fallible validation into
`main` or make every helper return `Result`, which is awkward for small
single-value validation helpers.

## Diagnosis or hypothesis

This is a checker rule about where `?` may appear, and it behaves
inconsistently across proc return shapes: `Unit`/`main` is fine, a stream
block nested in `main` is fine, but a value-returning `[error]` helper is not.
The constraint is not documented in the handbook, whose general statement
("postfix ? propagates that failure from a procedure whose effects include
error") led the agent to expect helpers to work. The result is repeated,
generalizable friction: every eval that wants a small typed validation or
parse helper hits the same wall and must inline or wrap. This is not
task-specific confusion and is not evaluator noise.

## North-star impact

Error propagation is a core XSH idiom; making `?` usable in any proc that
declares the `error` effect would let agents factor small fallible helpers
cleanly, improving ergonomics and learnability for every eval that composes
typed conversions. The falsification replay is a fresh `task-histogram` (and
at least one other helper-heavy eval) confirming that the inlining workaround
disappears and correctness is preserved.

## Proposed XSH change

Relax the `check.try-context` rule so postfix `?` is accepted in any
procedure that declares the `error` effect, not only in Result-returning or
`Unit`/top-level contexts. The handbook-only clarification is not an
alternative implementation for this ticket; it remains separate evidence.
